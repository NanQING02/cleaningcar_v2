# 板端验收清单

这份清单用于在 RKNN 板端做一轮正式验收，覆盖：

1. 环境安装
2. Web 服务启动
3. 推理启动与健康检查
4. 多路命名空间隔离
5. 截图、事件、单车视频
6. guardian 自动恢复

---

## 1. 验收前准备

先确认以下文件存在：

- `configs/config.json`
- `models/detection/best.rknn`
- `models/plate/plate_detect.rknn`
- `models/plate/plate_rec_color.rknn`
- `fonts/platech.ttf`
- `packages/` 下 RKNN 运行依赖

先确认以下配置口径：

- 单路运行：`system.device_id` 可填也可留空
- 多路运行：每份配置的 `system.device_id` 必须唯一
- `system.command_dir`
- `system.heartbeat_path`
- `system.startup_flag_path`
- `video.debug_frame_path`

说明：

- 上面 4 个运行时路径字段留空时，会自动隔离到 `/dev/shm/cleaningcar_runtime/<device_id或配置名>/`
- 如果仍沿用旧默认值，也会被运行时自动切到命名空间路径

若甲方设备还没有 `mppvideodec` 插件，本轮先保持：

```json
"video": {
  "hw_decode": false
}
```

相关背景见 `docs/部署验收/甲方MPP环境与补齐要求.md`。

## 2. 启动 Web（首次会自动安装环境）

在板端项目根目录执行：

```bash
cd /home/hinlink/3.17/2026.3.15cleaningcar-codex
chmod +x start_web_server.sh
./start_web_server.sh start
```

验收点：

- `venv-gst/` 创建成功
- 依赖安装过程中没有 RKNN / RGA 相关报错
- 浏览器能打开 `http://板端IP:8000/`
- 首页不是 `Template missing`
- `ss -ltnp | grep :8000` 能看到服务监听
- 手工模式下 `web_server_8000.log` 会持续写日志

## 3. Web 运行方式

### 3.1 手工模式

```bash
cd /home/hinlink/3.17/2026.3.15cleaningcar-codex
./start_web_server.sh start
./start_web_server.sh status
```

说明：

- `./start_web_server.sh` 会直接调用 `venv-gst/bin/python`
- 首次运行时会自动安装或修复 `venv-gst`
- 所以环境准备好后，可以不激活虚拟环境直接执行
- 只有需要手工跑 `python` 命令时，才建议先 `source venv-gst/bin/activate`

### 3.2 甲方自行配置 `systemd`（可选）

仓库不再提供自动安装脚本。如甲方需要 `systemd` 开机守护，请按根目录 `README.md` 中的 service 示例手工创建，再执行：

```bash
systemctl daemon-reload
systemctl enable --now cleaningcar-web
systemctl status cleaningcar-web --no-pager
```

## 4. 启动推理

### 4.1 单路

```bash
curl -X POST "http://127.0.0.1:8000/inference/start?key=config.json"
curl "http://127.0.0.1:8000/inference/status?key=config.json"
curl "http://127.0.0.1:8000/inference/health?key=config.json"
```

### 4.2 多路

```bash
curl -X POST "http://127.0.0.1:8000/inference/start?key=config.json"
curl -X POST "http://127.0.0.1:8000/inference/start?key=config_绕行.json"
curl "http://127.0.0.1:8000/inference/health?key=config.json"
curl "http://127.0.0.1:8000/inference/health?key=config_绕行.json"
```

重点看这些字段：

- `running=true`
- `pid` 有值
- `heartbeat.available=true`
- `heartbeat.healthy=true`
- `heartbeat.reason=ok`
- `runtime_namespace_key` 与当前配置对应
- `launch_id` 有值
- `heartbeat_path` 指向当前这一路自己的命名空间文件
- `restart_count` 不应异常增长

## 5. 必查项

### 5.1 推理日志

```bash
curl "http://127.0.0.1:8000/logs/inference?lines=100&key=config.json"
curl "http://127.0.0.1:8000/logs/files"
tail -n 100 logs/inference/infer_*.log
```

重点看：

- 是否成功加载检测模型
- 是否成功加载双模型车牌识别
- 是否出现 `Expected 6 outputs ... got 9` 一类后处理报错
- 是否出现持续重启、持续掉流、持续 backpressure

### 5.2 心跳文件

先取实际健康信息：

```bash
curl "http://127.0.0.1:8000/inference/health?key=config.json"
```

重点确认：

- `runtime_namespace_key`
- `launch_id`
- `heartbeat_path`
- `heartbeat.heartbeat.launch_id`
- `heartbeat.heartbeat.runtime_namespace_key`

如果返回里 `heartbeat_path` 为：

```text
/dev/shm/cleaningcar_runtime/RK3588-A/heartbeat.json
```

就直接查看该文件：

```bash
cat /dev/shm/cleaningcar_runtime/RK3588-A/heartbeat.json
```

正常情况下：

- `timestamp` 会持续刷新
- `last_progress_ts` 会持续前进
- `latest_frame_idx` 会持续增长
- `launch_id` 与 `/inference/health` 返回一致

### 5.3 启动信号

如果当前返回的 `runtime_namespace_key=RK3588-A`，且 `startup_flag_path` 留空或保持旧默认值，则默认启动标志路径为：

```text
/dev/shm/cleaningcar_runtime/RK3588-A/started.flag
```

启动截图默认目录仍是：

- `captures/startup/`

说明：

- 这是自动启动截图
- 推理第一次真正出结果后会自动保存，不需要手工触发

验收示例：

```bash
cat /dev/shm/cleaningcar_runtime/RK3588-A/started.flag
find captures/startup -type f | tail
```

验收点：

- 首次真正出结果后会生成启动标志文件
- 会保存一组启动截图
- 推理日志里能看到 `[startup-signal]`

### 5.4 手动保留截图

```bash
curl -X POST "http://127.0.0.1:8000/snapshot/keep?key=config.json" \
  -H "Content-Type: application/json" \
  -d "{\"tag\":\"board_check\",\"raw\":true,\"annotated\":true}"
```

验收点：

- 接口返回 `status=queued`
- 返回值里的 `command_file` 路径属于当前命名空间
- 该命令最终会被消费
- 会生成 `.done.json` 结果文件
- `captures/manual/` 下会新增截图

### 5.5 事件输出与截图

```bash
find events -maxdepth 2 -type f | tail -n 20
find captures -maxdepth 3 -type f | tail -n 20
```

重点看：

- 事件 JSON 是否产出
- `event_log.csv` 是否持续追加
- 事件截图是否和事件对得上
- `captureImage` 非空且文件真实存在

### 5.6 单车视频输出

默认输出目录：

- `video_result/per_id/`

验收点：

- 当 `logic.per_id_video_dir` 留空时，不应在项目根目录生成裸的 `YYYYMMDD/HH` 空目录
- 当配置目录不可写时，应自动回退到 `video_result/per_id/`
- 若单车视频不可写，只禁用单车视频，不影响主检测、事件 JSON 和截图链路
- Web 访问单车视频时要带 `key`，确保读到当前配置的目录

### 5.7 调试帧与辅助接口

```bash
curl "http://127.0.0.1:8000/debug_frame_meta?key=config.json"
curl "http://127.0.0.1:8000/frame_meta?key=config.json"
curl "http://127.0.0.1:8000/videos/per_id?key=config.json"
```

验收点：

- `debug_frame_meta` 读取的是当前配置的调试帧
- `frame_meta` 读取的是当前配置的视频源首帧
- `videos/per_id` 返回的是当前配置对应的单车视频列表

### 5.8 双模型车牌链路

重点确认：

1. 推理日志里没有车牌模型加载失败
2. 结果中能看到车牌文本与颜色结果
3. 当前只走双模型车牌链路，不再走旧单模型 LPR
4. 车型中文和车牌省份汉字不再显示 `??`

## 6. 多路隔离专项验收

如果板端要同时跑两路或更多路，必须加做这一步。

示例：

- `config.json` 的 `device_id=RK3588-A`
- `config_绕行.json` 的 `device_id=RK3588-B`

分别查询：

```bash
curl "http://127.0.0.1:8000/inference/health?key=config.json"
curl "http://127.0.0.1:8000/inference/health?key=config_绕行.json"
```

验收点：

- 两路 `runtime_namespace_key` 不同
- 两路 `heartbeat_path` 不同
- 两路 `launch_id` 不同
- 杀掉一路进程，不会导致另一路被误判为异常
- 旧心跳不会触发 `heartbeat_launch_mismatch` 以外的误重启连锁问题

## 7. 自启 / 卡死恢复验收

### 7.1 推理进程异常退出自启

先查推理 PID：

```bash
curl "http://127.0.0.1:8000/inference/status?key=config.json"
```

然后手动杀掉推理进程：

```bash
kill -9 <推理PID>
```

再观察：

```bash
watch -n 1 "curl -s 'http://127.0.0.1:8000/inference/status?key=config.json'"
```

验收点：

- `restart_count` 增加
- `running` 会恢复成 `true`
- guardian 日志里会出现进程退出和重启记录

### 7.2 心跳超时恢复

```bash
kill -STOP <推理PID>
```

等待超过：

- `system.heartbeat_timeout_seconds`
- 或 `system.progress_timeout_seconds`

再观察：

```bash
curl "http://127.0.0.1:8000/inference/health?key=config.json"
```

验收点：

- `heartbeat.reason` 会出现 `heartbeat_stale` 或 `progress_stale`
- 如果读到旧批次心跳，会看到 `heartbeat_launch_missing` 或 `heartbeat_launch_mismatch`
- guardian 会终止旧进程并重启当前配置对应的实例

## 8. `fp_output_mode=6/9` 对比验收

建议用同一段本地测试视频做 A/B，对比最稳定。

### 8.1 模式 6

```bash
source venv-gst/bin/activate
python run_zone_detect.py \
  --config configs/config.json \
  --video /path/to/test.mp4 \
  --source_mode file \
  --fp_output_mode 6 \
  --csv ./video_result/fp_mode6.csv
```

### 8.2 模式 9

```bash
source venv-gst/bin/activate
python run_zone_detect.py \
  --config configs/config.json \
  --video /path/to/test.mp4 \
  --source_mode file \
  --fp_output_mode 9 \
  --csv ./video_result/fp_mode9.csv
```

对比时至少看 4 件事：

1. 能否稳定跑完，不崩溃
2. 检测框数量是否明显异常
3. 误检、漏检是否变化
4. 事件类型和触发时机是否变化

当前默认策略：

- 默认 `6`
- 即使 FP 模型实际给出 `9` 个输出，也只取每个尺度的 `box + class`

## 9. 验收完成后的收口动作

通过后建议立即做这 4 件事：

1. 保存一份通过验收的正式配置
2. 保留一份通过验收的推理日志和关键截图
3. 记录当前 `device_id / runtime_namespace_key / 端口` 对应关系
4. 再做一次版本提交

如果有一项没通过，优先回传：

- `logs/inference/infer_*.log`
- `curl /inference/status?key=<配置名>` 返回值
- `curl /inference/health?key=<配置名>` 返回值
- 对应 `heartbeat_path` 指向的心跳文件
- 对应命名空间下的 `started.flag`
