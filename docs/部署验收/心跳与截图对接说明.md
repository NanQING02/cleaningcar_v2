# 心跳与截图对接说明

这份文档给甲方联调、板端部署和多路运行排查使用，重点说明 3 件事：

1. 心跳文件现在如何按 `device_id`/配置名自动隔离
2. Web 如何按 `key` 访问指定配置对应的推理实例
3. 手动截图命令如何下发、落盘和回查

---

## 1. 运行时命名空间

### 1.1 命名空间来源

当前项目的运行时文件不再默认共用一套固定路径，而是按下面顺序决定命名空间：

1. `system.device_id`
2. 当前配置文件名去掉后缀后的名称
3. 最终兜底 `default`

也就是：

- 多路运行时，优先要求每份配置的 `system.device_id` 唯一
- 如果 `device_id` 留空，运行时会退回当前配置文件名做隔离

### 1.2 自动隔离的默认路径

当下面这些字段留空、只填空白，或仍保持旧默认值时，运行时会自动切到：

- `system.command_dir`
- `system.heartbeat_path`
- `system.startup_flag_path`
- `video.debug_frame_path`

默认落点为：

- 命令目录：`/dev/shm/cleaningcar_runtime/<runtime_namespace_key>/cmd/`
- 心跳文件：`/dev/shm/cleaningcar_runtime/<runtime_namespace_key>/heartbeat.json`
- 启动标志：`/dev/shm/cleaningcar_runtime/<runtime_namespace_key>/started.flag`
- 调试帧：`/dev/shm/cleaningcar_runtime/<runtime_namespace_key>/debug.jpg`

其中 `<runtime_namespace_key>` 一般等于：

- `device_id` 清洗后的安全名称
- 或配置文件名清洗后的安全名称

### 1.3 什么时候不会自动改路径

如果你在配置里显式填写了自定义路径，并且它不等于旧默认值，系统会保留你的路径，不会强行改成命名空间路径。

## 2. 多路访问口径

### 2.1 Web 接口如何指定配置

多路运行时，Web 辅助接口要带 `key=<配置文件名>`，这样才会访问对应配置的：

- 推理进程状态
- 心跳
- 调试帧
- 手动截图命令目录
- 单车视频目录

示例：

```bash
curl "http://<设备IP>:8000/inference/health?key=config.json"
curl "http://<设备IP>:8000/inference/health?key=config_绕行.json"
curl "http://<设备IP>:8000/debug_frame_meta?key=config.json"
curl -X POST "http://<设备IP>:8000/snapshot/keep?key=config.json" \
  -H "Content-Type: application/json" \
  -d "{\"tag\":\"manual_check\",\"raw\":true,\"annotated\":true}"
```

### 2.2 建议甲方优先读哪个接口

优先读：

- `GET /inference/health?key=<配置名>`

这个接口已经把 guardian 判断结果整理好了。甲方通常只需要关注：

- `running`
- `heartbeat.healthy`
- `heartbeat.reason`
- `runtime_namespace_key`
- `device_id`
- `launch_id`
- `heartbeat_path`

典型返回里会包含：

```json
{
  "running": true,
  "pid": 12345,
  "restart_count": 1,
  "runtime_namespace_key": "RK3588-A",
  "device_id": "RK3588-A",
  "launch_id": "abc123def456",
  "heartbeat_path": "/dev/shm/cleaningcar_runtime/RK3588-A/heartbeat.json",
  "heartbeat": {
    "available": true,
    "healthy": true,
    "reason": "ok"
  }
}
```

## 3. 心跳判活口径

### 3.1 常用字段

- `running`
  - 当前 guardian 认为这一路推理进程是否在运行
- `heartbeat.available`
  - 是否读到了对应命名空间下的心跳文件
- `heartbeat.healthy`
  - 当前这一路是否健康
- `heartbeat.reason`
  - 不健康或过渡状态的原因
- `runtime_namespace_key`
  - 当前这一路的运行时命名空间 key
- `launch_id`
  - 当前这次启动的唯一标识，用来区分新旧进程
- `heartbeat_path`
  - 当前实际读取的心跳文件路径

### 3.2 常见 `heartbeat.reason`

- `ok`
  - 正常
- `starting`
  - 启动宽限期内，暂不判故障
- `not_started`
  - 还没启动推理
- `heartbeat_missing`
  - 没找到心跳文件
- `heartbeat_pid_mismatch`
  - 心跳文件里的 `pid` 不是当前这一路对应的进程
- `heartbeat_launch_missing`
  - 心跳里没有 `launch_id`
- `heartbeat_launch_mismatch`
  - 心跳里的 `launch_id` 不是当前这次启动的实例
- `heartbeat_old`
  - 读到的是旧心跳文件
- `heartbeat_stale`
  - 心跳时间戳过旧
- `progress_missing`
  - 心跳里缺少处理推进时间
- `progress_stale`
  - 心跳还在写，但处理流程长时间没有推进

### 3.3 为什么现在能避免多路误重启

因为 guardian 不再只看一个公共心跳文件，而是同时比对：

- 当前配置对应的命名空间
- 当前推理进程 PID
- 当前启动批次的 `launch_id`

所以：

- 重启 Web 不会误杀别的配置对应的推理
- 重启某一路推理，不会把另一条路的心跳误判成当前路的心跳

## 4. 手动截图对接

### 4.1 接口语义

`POST /snapshot/keep` 是异步入队，不是同步返回图片。

流程是：

1. Web 把截图请求写成 `*.cmd.json`
2. 对应推理实例轮询自己的命令目录
3. 推理进程用当前缓存帧保存截图
4. 成功后写 `*.done.json`
5. 失败后写 `*.failed.json`

### 4.2 请求示例

```bash
curl -X POST "http://<设备IP>:8000/snapshot/keep?key=config.json" \
  -H "Content-Type: application/json" \
  -d "{\"tag\":\"party_a\",\"raw\":true,\"annotated\":true}"
```

请求体：

```json
{
  "tag": "party_a",
  "raw": true,
  "annotated": true
}
```

约束：

- `raw` 和 `annotated` 不能同时为 `false`

返回示例：

```json
{
  "status": "queued",
  "command_file": "/dev/shm/cleaningcar_runtime/RK3588-A/cmd/snapshot_20260325_153000_abcd1234.cmd.json"
}
```

说明：

- `status=queued` 只表示命令已入队
- `command_file` 是本次命令文件的实际路径
- 真正截图是否成功，要看同目录下的 `*.done.json` 或 `*.failed.json`

### 4.3 结果文件

成功时：

- `*.done.json`

失败时：

- `*.failed.json`

成功示例：

```json
{
  "status": "done",
  "cmd": "keep_snapshot",
  "frame_idx": 18234,
  "captures": {
    "raw": "captures/manual/20260325/15/20260325_153000_f018234_party_a_raw.jpg",
    "annotated": "captures/manual/20260325/15/20260325_153000_f018234_party_a_annotated.jpg"
  }
}
```

常见失败原因：

- `no frame cached yet`
  - 推理刚启动，还没有可截图的缓存帧
- `snapshot save failed`
  - 目录不可写、磁盘空间不足或编码失败
- `raw/annotated cannot both be false`
  - 请求参数不合法

## 5. 联调建议

### 5.1 HTTP 联调建议

推荐甲方按下面口径联调：

1. 轮询 `GET /inference/health?key=<配置名>`
2. 以 `running=true` 且 `heartbeat.healthy=true` 作为这一路正常的主判断
3. 手动截图通过 `POST /snapshot/keep?key=<配置名>` 下发
4. 如果需要拿结果：
   - 直接共享截图目录
   - 或读取 `command_file` 同目录下的 `*.done.json`

### 5.2 同机部署建议

如果甲方程序和项目跑在同一台板子上，也可以直接读写运行目录：

- 读取：`heartbeat_path`
- 写入：`command_dir/*.cmd.json`
- 回查：`*.done.json` / `*.failed.json`

但即使同机部署，仍然建议先通过 Web 的 `health` 接口拿实际路径，避免写死旧默认值。

---

## 6. 结论

当前正式口径是：

- 多路运行必须保证 `system.device_id` 唯一
- 运行时辅助文件默认按 `device_id`/配置名自动隔离
- 多路访问必须带 `?key=<配置名>`
- 心跳判活不仅看 PID，还看 `runtime_namespace_key + launch_id`
- `POST /snapshot/keep` 是异步命令，不是同步取图接口
