# 部署前性能评估与低风险优化建议

> 阅读前说明
>
> - 本文最初服务于一轮"甲方板端缺少 `ffmpeg rkmpp` 与 `mppvideodec`、交付口径偏软件解码"的双路评估。
> - 当前仓库 `configs/config.json` 已改为现场三核分配口径：`video.hw_decode=true`、`video.workers=1`、冲洗道主检测+车牌用 NPU core 0、绕行道主检测+车牌用 core 1、双车轮旁路用 core 2，`logic.enable_per_id_video=true`、`wheel.enabled=true`。
> - 如果用于双路或长期性能压测，应按本文建议关闭调试叠加、调试帧写图或单车视频等高开销项。
> - 当前代码在 `cleaningcar/video_io.py` 中会先尝试 `FFmpeg` 硬解，再尝试 `GStreamer+mpp`，最后才回退到软解；单车视频写出顺序是 `FFmpeg 硬编 -> GStreamer 硬编 -> FFmpeg libx264`。

本文档用于在双路部署、长稳压测或资源紧张场景下评估推理开销，并给出收益较快、风险较低的优化建议。

## 1. 当前项目的实际多路实现方式

当前项目的多路不是"一个进程内统一调度多视频源"，而是：

- Web 端按配置文件 `key` 维护多个 `InferenceManager`
- 每个 `InferenceManager` 启动一个独立的 `run_zone_detect.py` 进程
- 每个推理进程内部再启动自己的 reader、worker、tracking、events、snapshot、per-id video、cleanup

也就是说，双路推理当前等价于：

- 2 个独立 Python 推理进程
- 2 套独立的读流与跟踪链路
- 2 套独立的事件、截图、心跳和日志输出

这类实现方式的优点是隔离性好，单路故障不容易直接拖死另一条；缺点是资源开销基本按路数近线性增长。

## 2. 双路推理的资源开销判断

若在同一块板子上同时开两路，当前实现的开销主要落在以下 5 个部分。

### 2.1 CPU 开销

主要来自：

- 未命中 `FFmpeg` / `GStreamer+mpp` 硬解时的软件解码
- OpenCV 读流
- 检测后处理
- 车牌检测与识别的前后处理
- 叠框、叠字、调试画面写图
- 事件截图 JPEG 编码
- 单车视频编码，尤其是回退到 `FFmpeg libx264` 时的 CPU 开销

在硬解两级都不可用或单车视频退到 `libx264` 的口径下，CPU 通常是双路部署最先吃紧的资源。

### 2.2 NPU 开销

每条链路都会加载并执行：

- 主检测模型
- 车牌检测模型
- 车牌识别/颜色模型

因此双路开启后，NPU 推理负载也会明显上升。若两路都配置较高的 `workers`，容易出现：

- 实际 FPS 下降
- 队列堆积
- 心跳变慢
- RTSP 掉帧或 guardian 误判卡死

### 2.3 内存开销

每路都会重复占用：

- 模型内存
- 帧缓存
- `task_q` / `result_q`
- 跟踪与事件状态
- Web/心跳/日志缓冲

双路时常见表现是 RSS 和系统内存占用同步抬升。

### 2.4 I/O 开销

当前项目里 I/O 开销较敏感的部分有：

- 调试画面文件写入 `video.debug_frame_path`
- 事件截图
- 启动截图 / 手动截图
- 单车视频 `video_result/per_id`
- 推理日志 `logs/inference`

在双路下，这些写盘或 `/dev/shm` 写入都会叠加。

### 2.5 温度与长期稳定性

双路跑 10 到 15 分钟不出问题，不代表长时间一定稳定。真正上线前仍需确认：

- 温度是否持续爬升
- `restart_count` 是否开始增长
- `heartbeat.reason` 是否长期保持 `ok`
- 解码 FPS、管线 FPS 是否明显下跌

## 3. 当前主配置下的开销重点

当前仓库主配置下，`workers` 已经降到 `2`，但调试帧默认会写入命名空间路径，且 `logic.no_draw=false`、`logic.draw_plate_boxes=true`、`enable_per_id_video=true`、检测 CSV 持续写入、事件截图与 `base64` 上报、车轮旁路默认开启。单车视频在部分板端可能退到 `libx264`，主线程也同时承担读流和结果组装，这些都是双路或长稳压测时值得重点关注的开销点。

## 4. 双路部署前必须先做的评估

建议按下面顺序评估，不要一步到位直接双路上线。

### 第 1 阶段：单路基线

先只开 1 路，连续跑 10 到 15 分钟，记录：

- `/inference/status`
- `/inference/health`
- 推理日志中的 `[perf]`
- 推理日志中的 `[monitor]`
- `restart_count`
- 事件、截图、单车视频是否正常

若单路本身还不稳，不要直接上双路。

### 第 2 阶段：双路压测

在单路稳定后，再开第二路，并重点观察：

- 两路 `restart_count` 是否上涨
- 两路 `heartbeat.reason` 是否保持 `ok`
- `[perf] 解码FPS` 是否明显下降
- `[perf] 管线FPS` 是否明显下降
- 是否出现持续 `backpressure`
- 车牌识别和事件触发是否延迟明显增加

### 第 3 阶段：长稳验证

双路至少连续运行一轮更长时间验证，建议：

- 30 分钟起步
- 再根据实际板端发热和业务节奏决定是否延长

## 5. 双路部署前的目录与配置注意项

双路若使用不同配置文件，必须确保每路关键运行路径互不冲突，至少确认：

- `system.heartbeat_path`
- `system.startup_flag_path`
- `video.debug_frame_path`
- `system.metrics_path`
- `event_output_dir`
- `event_capture_dir`

否则会出现：

- 心跳相互覆盖
- 调试画面被另一条链路覆盖
- 事件文件混写
- 现场误判是哪一路出了问题

`system.device_id` 是这些路径自动隔离的主键，多路部署必须保证唯一。

## 6. 本轮收益最快、风险最小的优化顺序

以下排序按"交付阶段优先、改动小、收益快"给出。

### 优先级 1：关闭调试叠加与调试画面写图

这是本轮最推荐的优化项。

建议在双路压测时关闭：

- `logic.debug_overlay`
- `logic.debug_track_state`
- `logic.debug_anchor_points`
- `logic.debug_water_boxes`

同时建议：

- 将 `video.debug_frame_path` 显式置为 `off`
- 或至少显著增大 `video.debug_frame_interval`

收益：

- 直接减少叠图 CPU
- 直接减少 JPEG 编码和文件写入
- 对业务逻辑零侵入

风险：最低。

影响：只影响实时调试画面，不影响事件、车牌、跟踪主链路。

### 优先级 2：双路固定每路 `workers=1`

当前仓库默认 `config.json` 与 `config_绕行.json` 均为 `video.workers=1`。现场双路按三核分配运行：冲洗道主检测+车牌 core 0，绕行道主检测+车牌 core 1，双车轮旁路 core 2；不要盲目上调 worker 数。

收益：

- 降低 NPU/CPU/DDR 争用
- 降低队列堆积和心跳超时风险

风险：低。

影响：单路极限吞吐可能下降，但双路总稳定性通常更容易提升。

建议口径：

- 单路调试：可继续使用 `2`（或临时调到 `3`）
- 双路试运行：优先每路 `2`

### 优先级 3：双路试运行阶段临时关闭单车视频

若现场重点先验证事件和识别链路，建议双路首轮压测可临时关闭：

- `logic.enable_per_id_video=false`

收益：

- 明显减少单车视频编码和磁盘 I/O，尤其是在编码退到 `libx264` 时
- 更容易先把双路主链路跑稳

风险：低。

影响：会失去按车辆 ID 的录像产物。若业务必须保留单车视频，可作为第二轮恢复项。

### 优先级 4：降低源侧输入压力

若摄像头或上游流媒体可调，优先从源头控制：

- 分辨率
- 码率
- FPS

这类优化对软件解码收益通常最直接。

收益：CPU 降幅通常最明显。

风险：低到中。

影响：可能影响远距离识别效果，需要现场平衡。

### 优先级 5：控制日志频率

当前项目已有 `[perf]` 和 `[monitor]` 日志。交付期不建议做代码级日志系统重构，但可先控制：

- `system.monitor_interval`
- 人工查看日志频率

收益：有一定帮助。

风险：很低。

影响：主要是减少日志噪声，收益小于前几项。

## 7. 本轮不建议推进的优化项

以下项有潜在收益，但本轮交付阶段不建议立即作为主动作：

- 甲方设备硬件加速环境收口
- 大幅调整事件链路或多路调度架构
- 重写 Web 调试画面实现方式
- 大规模重构日志系统

原因不是这些项没有价值，而是：

- 环境依赖重
- 验证成本高
- 容易把交付节奏拖慢

## 8. 本轮推荐部署策略

### 单路正式交付

- 若目标板已确认既缺少 `ffmpeg rkmpp`、也缺少 `mppvideodec`，可显式设置 `video.hw_decode=false`
- 若目标板具备可用的 `ffmpeg rkmpp`，优先保留 `video.hw_decode=true`
- 若目标板没有 `ffmpeg rkmpp` 但具备可用的 Rockchip MPP 插件，也可保留 `video.hw_decode=true`，由程序自动退到 `GStreamer+mpp`
- 双路压测时关闭调试叠加和调试帧写图
- 保留业务必需的事件、截图、车牌和录像

### 双路试运行

- 每路固定从 `workers=1` 起步
- 先关闭调试叠加
- 第一轮可临时关闭 `enable_per_id_video`
- 跑稳后再逐步恢复单车视频

## 9. 现场验收建议

若要判断双路是否可上线，至少同时满足：

- 两路 `restart_count` 不持续增长
- 两路 `/inference/health` 长时间保持 `ok`
- 心跳帧号持续增长
- 事件仍正常产生
- 截图和车牌识别没有明显退化
- 运行 10 到 15 分钟后没有明显性能恶化

若任一项不满足，优先从以下顺序回退：

1. 关闭调试叠加与调试画面
2. 下调 `workers`
3. 关闭单车视频
4. 再考虑源侧降分辨率 / 降 FPS
