## 3. 专项结论（2026-09-23 追问核实）

### 3.1 车轮 reader 的全帧拷贝是不是手写 GS 读流引入的？能不能改回去？

**是 `2e4377b` 引入的，但不建议改回去。**

- 修复前：wheel 用共享的 `create_video_reader`（cv2.VideoCapture + GStreamer 管线字符串），OpenCV 按 `read()` 消费节奏拉样本，空闲时不动。
- 修复后：手写 PyGObject reader 为解决甲方相机 RTP-Info seq-base 错误宣告（每次 PLAY 宣告 seq=1/rtptime=0，实际序号全局连续，jitterbuffer 把首包当旧包丢弃数十至数百秒），在 caps 协商时移除错误的 seqnum-base/clock-base。**改回去 = 车轮缺照片问题复发**。
- 新 reader 代价：`emit-signals=True` 使 `_on_new_sample` 回调对每个解码帧做 copy #1（`wheel_gstreamer.py:352`），`read()` 再做 copy #2（`:437`）。已确认 appsink 配置 `sync=false drop=true max-buffers=N`（`:237-240`）。
- **正确修法（保留 RTP-Info 修复）**：
  1. 去掉 copy #2：`read()` 改为所有权交接（把 `_latest_frame` 置 None 拿走数组，回调侧发现为 None 时再分配）；
  2. 空闲期跳过 copy #1：回调里当"推理未激活且消费者超过 200ms 未读"时只更新 seq/fps/时间戳，不做 `.copy()`（例如每 4 帧保留 1 帧作为新鲜 latest），这同时就是 `reader_idle_fps` 的真实落地；
  3. 连接稳定性不受影响：管线始终 PLAYING，RTSP 长连，fps 只影响拷贝频率不影响连接。

### 3.2 `per_id_video_source=raw` 的 raw_frame_cache 是不是 c9a8d24 的负优化？

**不是。`copy_raw_frame_cache` 自初始提交 `8d9eb55` 就存在，c9a8d24 只改了 `worker.py` 的 draw_frame 逻辑。** 各模式每帧整帧复制次数对比：

| 模式 | c9a8d24 前 | c9a8d24 后 |
| --- | ---: | ---: |
| 录像关闭 | 1（worker draw copy） | 0 |
| auto | 1 | **0**（raw cache 存引用） |
| raw | 2（worker copy + raw cache copy） | 1（仅 raw cache copy） |
| annotated | 1 | 1 |

结论：以 `c9a8d24` 当时的代码看，各模式均未变差。后续 `197c32b` 又删除了显式 raw 的强制 copy，因此当前默认配置下 raw 与 auto 都是0次额外整帧复制；只有显式设置 `logic.copy_raw_frame_cache=true` 才恢复防御性复制。实测报告数字是"录像整体关闭"场景，不能直接等同于完整生产组合。

### 3.3 NPU 核分配：车牌挪 core2 有没有本地证据？

**没有本地 A/B 记录**（2号设备报告里 core2=0% 是因为没接车轮；3号快照只有 core0 32%/core1 55% 的静态值）。风险定性：

- 正确性无风险：RKNNLite `core_mask` 只是绑定 NPU core，同核多上下文按时间片调度，不会出错，只影响时延。
- 吞吐上有取舍：车牌推理高峰（车在场）与车轮激活期（同样是车在场）高度重叠，plate 挪 core2 会与车轮抢核；但车牌与主检测同核 0 是**纯串行排队**，两者必居其一。
- 另注意：`plate_core_mask` 留空走 `resolve_auto_plate_mask` 会自动挑 **core1**（`pipeline.py:1297` 的 spare 逻辑），那是绕行道进程的核，跨进程抢核，不推荐 auto。
- 建议：在板端做一次 `plate_core_mask="2"` 的 A/B（主检测单帧时延、车牌触发帧延迟、core2 占用、车轮照片完整率各记一轮），有数据再定。

### 3.4 5fps vs 20fps 对用户目标的影响

用户目标 = 连接稳定不断流 + 照片可识别可绑定。结论：**帧率设置不影响连接稳定性**（reader 常开管线常 PLAYING）；激活期 20fps 提供更多 0.5s 桶内候选、代表帧选优更好，建议激活期维持 20，只做空闲期降拷贝（见 3.1）。

本地修复为每track/side保留有界已处理entryId（4096/侧），provider历史entry只消费一次；主线程和type5 prewait线程通过RLock串行更新。回归测试模拟60个entry、3桶上限、连续21次provider重放，保存次数固定为首次60次，后续不再增长。该修复阻断重复水化放大，不改变0.5秒桶式批量上报口径；基础照片保留策略仍需单独产品决策。

### 9.8 机动车统一续轨与业务生命周期再捕获（2026-10-01）

6000/6002实机事件证明，远距低置信漏检、dump/yellow跨类框和无牌handoff硬门槛会把同车拆成多个event。分两层整改：

- 检测输入层：车辆超类做class-agnostic NMS；`vehicle_tracking_min_confidence=0.4`保留低置信框续轨，具体车型原业务阈值仍决定是否允许type1/type2。
- 生命周期层：标准配置增加30秒 `lifecycle_reacquire_seconds`；稳定车牌接续允许重型车辆子类兼容；无牌只在唯一、空间连续、方向不冲突时handoff，并继承event阶段、录像状态和车型投票。

历史配置未出现新字段时EventManager继续沿用`track_lost_grace_seconds`，避免直接调用方静默改变。相关检测、配置、事件和生命周期专项回归通过；仍需用6000绿色工程车和6002拆段样本做相同输入实机A/B。

### 9.9 单车录像真实时基（2026-10-01）

6002完整场景中，录像开启且车轮活动的55个资源样本显示管线均值约7.32 FPS；相同车轮活动、录像关闭的16个样本均值约9.83 FPS，关闭录像的观测提升约34%，但仍显著低于车轮未活动且录像关闭时约19.38 FPS。因此录像编码是明显额外负载，双车轮推理及共享NPU/内存带宽竞争仍是主要限制，不能把关闭录像视为完整性能修复。

旧实现把所有实际处理帧固定按配置25 FPS写入MP4：例如墙钟约50秒只处理约250帧时，文件时长只有约10秒，播放表现为加速。现在每帧同时传入采集时间，编码完成后用FFmpeg stream copy修正容器时间戳，不二次编码；修正失败时保留原始可播放文件。板端type6事件JSON记录`videoFileDuration`便于核对实际MP4时长，平台type6上报字段保持不变。
