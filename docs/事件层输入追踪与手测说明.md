# 事件层输入追踪与手测说明

## 目的

事件输入追踪用于记录“检测、跟踪和绑定完成后，事件状态机实际收到什么”，帮助在不改模型、不连接甲方测试接口的情况下，逐个视频人工验证事件逻辑。

追踪默认关闭，不保存视频帧或Base64图片，也不会在元数据中记录RTSP用户名和密码。

## 开启方式

在Web开发者参数中设置：

```json
{
  "logic": {
    "event_trace_enabled": true,
    "event_trace_dir": "event_traces",
    "event_trace_queue_size": 4096,
    "track_lost_grace_seconds": 8.0
  }
}
```

保存配置并重启对应推理进程后生效。手测结束后建议关闭 `event_trace_enabled`，避免长期产生追踪文件。

## 推荐手测步骤

1. 复制一份独立配置文件，设置本地视频路径和 `source_mode=file`。
2. 在Web中选择这份配置并调整Zone A、Zone B和流向。
3. 记录人工预期：车辆数量、每辆车进入/离开方向、是否进入清洗区、是否应产生type1～type6。
4. 开启事件输入追踪并运行本地视频一次。
5. 等待文件源自然结束，不开启自动重启。
6. 检查事件JSON、截图、推理日志和本次trace目录。
7. 将视频、配置文件、人工预期和trace目录作为一个固定案例保存。

## 输出目录

每次运行生成独立目录：

```text
event_traces/<配置名>/<运行时间_pid_随机后缀>/
  run.json
  frames.jsonl
  events.jsonl
  summary.json
```

- `run.json`：配置名、设备ID、脱敏后的视频源、源FPS和本次Zone快照。
- `frames.jsonl`：车辆检测、tracker分配、保留中的ID、丢帧、车牌/水流输入和Zone变化。
- `events.jsonl`：实际生成的事件和被抑制的阶段倒退。
- `summary.json`：各类记录数量、事件类型数量和追踪队列丢记录数。

## 人工检查重点

### ID连续性

- 检测短暂消失后是否继续使用原tracker ID。
- `retainedTrackIds`仍包含某ID时，该ID的事件状态是否一直保留。
- 输入25 FPS时，8秒宽限对应200帧；事件状态额外保留1秒，对应225帧。

### 事件顺序

- type1单独出现时可以保存在本地，但不应立即上传。
- type2成立时，同ID必须先产生type1，再产生type2。
- type3和type4允许因实际业务条件缺失，不强制伪造。
- 已进入更高阶段后，不得再对外发送更低阶段；此类情况应记录为 `sequence_issue`。
- 正常完整流程期望单调前进：`1 -> 2 -> 3 -> 4 -> 5 -> 6`。

### 模型与事件逻辑分离

- 画面中不存在车辆却检测到车辆：标记为纯模型误检，加入困难负样本。
- 真实车辆存在但不应进入业务流程：由Zone、门线和生命周期逻辑处理。
- 本阶段不通过修改车辆阈值掩盖事件时序问题。
