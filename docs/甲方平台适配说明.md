# 甲方平台适配说明

本文档说明从 `3ec8a30e15b6de603837129e5af38f759dc9ffc7` 升级到当前最新版本后，甲方平台需要适配的接口和文件访问变化。接口行为对应业务代码提交 `76f2442970f8fb6e247b26d000a7b565cb7a857b`。

## 结论

甲方平台的主事件接口地址、请求方式和认证方式不变：

- 主事件接口：`POST /api/vehicle/wash-event`
- 车轮照片接口：`POST /api/vehicle/wheel-photo`
- 请求格式：`Content-Type: application/json`
- Token：仍使用 `Authorization: Bearer <token>`

需要重点调整的是图片字段：车辆事件截图和轮胎图片都改为路径方式，平台不再按 base64 解码这些字段。

## 变更清单

| 项目 | 旧版本 `3ec8a30e` | 当前版本 | 甲方需要调整 |
| --- | --- | --- | --- |
| 主事件截图 `captureImage` | 默认按 base64 上报 | 默认按路径上报 | 不再 base64 解码，改为按文件路径读取或转 URL |
| 事件截图目录 | `captures/<配置名>` | `/data/ftp/event_captures/<配置名>` | 确认平台可访问 `/data/ftp/event_captures` |
| 事件截图质量 | 85 | 70 | 不需要改接口，图片体积会下降 |
| `type=5` 车轮结果图片 | `wheelResults[].imageBase64` | `wheelResults[].photoUrl` | 接收 `photoUrl`，不要再依赖 `imageBase64` |
| 车轮照片目录 | `/data/ftp/box/...` | `/data/ftp/box/...` | 继续以 `/data/ftp` 为文件根目录 |
| 车轮照片批量接口 | 已存在 `wheel-photo` | 最终 `type=5` 时一次性入上传队列 | 不要按“每次识别立即到达”设计 |
| 配置文件 | `configs/config.example.json` | `configs/config.json` | 部署脚本若引用旧示例文件名，需要改为正式配置文件 |

## 主事件截图

当前配置为：

```json
"system": {
  "api": {
    "capture_mode": "path"
  }
},
"event_capture_dir": "/data/ftp/event_captures/config"
```

主事件中的 `captureImage` 示例：

```json
{
  "id": "RK3588-DEV-202607132100-12",
  "type": 5,
  "captureTime": "2026-07-13 21:00:36",
  "captureImage": "/data/ftp/event_captures/config/20260713/21/20260713_210036_RK3588-DEV_12_t5_f889.jpg"
}
```

甲方平台处理方式：

1. 将 `captureImage` 当作图片文件路径字符串保存。
2. 如果平台通过挂载目录读取，直接读取该绝对路径。
3. 如果平台通过 HTTP/FTP 读取，需要把 `/data/ftp` 映射成文件服务根地址。

例如文件服务根目录是 `/data/ftp`，HTTP 地址是 `http://板端IP/`：

```text
板端路径：
/data/ftp/event_captures/config/20260713/21/a.jpg

平台访问地址：
http://板端IP/event_captures/config/20260713/21/a.jpg
```

## 车轮结果图片

当前 `type=5` 主事件会附加该车生命周期内锁定的左右轮结果。字段已从 `imageBase64` 改为 `photoUrl`。

当前 payload 示例：

```json
{
  "id": "RK3588-DEV-202607132100-12",
  "type": 5,
  "captureTime": "2026-07-13 21:00:36",
  "captureImage": "/data/ftp/event_captures/config/20260713/21/20260713_210036_RK3588-DEV_12_t5_f889.jpg",
  "washEndTime": "2026-07-13 21:00:36",
  "videoEndTime": "2026-07-13 21:00:38",
  "totalWashDuration": 7.3,
  "videoDuration": 12.5,
  "cleanliness": 0,
  "plateNumber": "鲁A12345",
  "plateConfidence": 0.98,
  "plateColor": "蓝色",
  "plateColorConfidence": 0.92,
  "vehicleType": "小汽车",
  "vehicleTypeConfidence": 0.91,
  "lane": "冲洗",
  "plateIsGuess": false,
  "plateRecognitionAbnormal": false,
  "direction": 5,
  "directionLabel": "正向前出",
  "wheelResults": [
    {
      "side": "left",
      "captureTime": "2026-07-13 21:00:30",
      "photoUrl": "box/20260713/21/143025_12_left_1.jpg",
      "className": "50-75"
    },
    {
      "side": "right",
      "captureTime": "2026-07-13 21:00:31",
      "photoUrl": "box/20260713/21/143025_12_right_1.jpg",
      "className": "75-100"
    }
  ]
}
```

`photoUrl` 是相对 `system.wheel_photo_base_dir` 的路径。当前默认：

```json
"system": {
  "wheel_photo_base_dir": "/data/ftp"
}
```

因此：

```text
photoUrl:
box/20260713/21/143025_12_left_1.jpg

板端实际文件：
/data/ftp/box/20260713/21/143025_12_left_1.jpg

HTTP 映射示例：
http://板端IP/box/20260713/21/143025_12_left_1.jpg
```

甲方平台需要做的修改：

1. `wheelResults` 子项里不要再强依赖 `imageBase64`。
2. 新增或改用 `photoUrl` 字段。
3. 图片展示、下载、归档逻辑按 `/data/ftp` 文件根目录映射。
4. 过渡期建议兼容两种字段：优先读 `photoUrl`，没有 `photoUrl` 时再兼容旧的 `imageBase64`。

## 车轮照片批量接口

独立车轮照片接口仍然是：

```text
POST /api/vehicle/wheel-photo
```

如果 `system.api.wheel_photo_url` 留空，程序会从主事件接口自动推导：

```text
主事件：
http://host:port/api/vehicle/wash-event

车轮照片：
http://host:port/api/vehicle/wheel-photo
```

请求 payload 示例：

```json
{
  "photoUrl": "box/20260713/21/143025_12_left_1.jpg",
  "type": "4",
  "cleanValue": 3
}
```

字段说明：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `photoUrl` | string | 相对 `/data/ftp` 的车轮图片路径 |
| `type` | string | 车轮侧别，左侧为 `"4"`，右侧为 `"5"` |
| `cleanValue` | number | 清洁度值，`0-25` 为 1，`25-50` 为 2，`50-75` 为 3，`75-100` 为 4 |

发送时机：

- 不是每次旁路识别到车轮就立即 HTTP 上报。
- 车辆生命周期内会按 `wheel.photo_bucket_seconds` 分桶缓存和落盘代表图。
- 最终 `type=5` 事件触发时，把该车生命周期内的代表车轮照片一次性加入上传队列。
- 上传队列异步发送，失败会重试，因此平台侧应按 `photoUrl` 做幂等处理，避免重复入库。

## 文件访问要求

甲方平台必须具备以下任一能力：

1. 直接挂载板端 `/data/ftp`，按文件路径读取。
2. 通过 FTP 暴露 `/data/ftp`。
3. 通过 HTTP 静态服务暴露 `/data/ftp`。

推荐平台侧统一实现一个路径转换函数：

```text
输入：
/data/ftp/event_captures/config/20260713/21/a.jpg

输出：
http://板端IP/event_captures/config/20260713/21/a.jpg
```

```text
输入：
box/20260713/21/143025_12_left_1.jpg

输出：
http://板端IP/box/20260713/21/143025_12_left_1.jpg
```

## 兼容建议

为了平滑切换，甲方平台可以按以下优先级解析图片字段：

1. 如果 `captureImage` 以 `/data/ftp/` 开头，按板端文件路径处理。
2. 如果 `captureImage` 看起来是 base64，走旧解码逻辑。
3. 对 `wheelResults`，优先使用 `photoUrl`。
4. 如果 `wheelResults[].photoUrl` 为空，再兼容旧字段 `imageBase64`。

完成切换后，可以移除主事件截图和轮胎图片的 base64 解码依赖。

## 验收点

甲方平台联调时建议确认：

- `wash-event` 能接收 `captureImage` 路径字符串。
- `type=5` 事件能接收 `wheelResults[].photoUrl`，且不要求 `imageBase64`。
- 平台能根据 `captureImage` 打开事件截图。
- 平台能根据 `wheelResults[].photoUrl` 打开轮胎图片。
- `/api/vehicle/wheel-photo` 能接收 `{photoUrl,type,cleanValue}`，并能处理重复 `photoUrl`。
- 文件服务根目录确实指向板端 `/data/ftp`。
- 平台接口返回 2xx 后，板端上传队列会认为该条发送成功。
