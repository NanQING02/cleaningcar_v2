## 3. 当前基线

### 3.1 性能与运行状态

- 主视频输入约 `20 FPS`。
- 当前模型检测及后续处理通常为 `17～19 FPS`。
- 第一阶段以稳定性和事件正确性为优先目标，暂不要求强行追满 `20 FPS`。
- 办公室2号设备的 GStreamer `mppvideodec` 已确认支持 `BGR` 和 `DMABuf` 输出。
- 四个 RKNN 模型与办公室设备生产旧副本逐文件一致：主检测、车牌检测、车牌识别/颜色、车轮检测。

### 3.2 自动测试基线

- 板端现有 `venv-gst` 可导入 `numpy`、`cv2`、`fastapi`、`pydantic` 和 `rknnlite`。
- 板端未安装 `pytest`，现有25个测试文件均基于标准库 `unittest`，可直接运行。
- 完整测试共 `191` 项：`189` 项通过，`2` 项失败。
- 两项失败来自同一个旧断言：`test_site_config_runtime.py` 仍期望 `video.decode_backend=auto`，而两份现场配置已经固定为 `gstreamer`。
- 跟踪8项、事件36项、解码21项、Web 20项、车轮51项分类测试均通过。

### 3.3 已知架构问题

- 事件状态在 `track_timeout_frames=80` 时删除，但 ByteTrack 在 `track_max_age=100` 后才删除轨迹，可能让同一个 tracker ID重新建立空事件状态。
- 业务事件身份直接依赖短期 tracker ID，缺少跨ID、跨遮挡和跨进程重启的车辆生命周期。
- 新目标只要首次出现在 Zone A 内，就可能被当作新进场车辆。
- 水流判断目前没有可靠绑定到具体车辆，画面中的任意水流框可能影响多个已进入清洗区的轨迹。
- 当前上报采用 type1～type6 多阶段请求，必须确保同一车辆始终使用同一个业务ID，并由甲方按ID更新同一条记录。
- 当前 Web 主要是配置和运维后台，尚无面向甲方的事件台账、复核、纠错和审计能力。
- 2026-08-30 双路实测中的52条绕行事件经人工复核属于纯模型误检，可能同时受困难负样本不足和类别阈值偏低影响。
- 绕行道每2帧固定执行一次全图双模型车牌链路；冲洗道仅在主检测存在车辆候选时执行，因此两路管线FPS存在明显差异。
- 2026-08-31 RKNNLite运行时确认 `plate_detect.rknn` 和 `plate_rec_color.rknn` 均为 FLOAT16，不是 INT8。
- 本次实测发现type2可能早于type1；迟到的type1会留在上传缓冲区，无法被已经发生过的type2再次flush。

## 4. 解码与RGA硬约束

### 4.1 主路RTSP唯一允许链路

```text
RTSP
  -> GStreamer rtspsrc
  -> depay / parse
  -> mppvideodec
  -> video/x-raw, format=BGR
  -> appsink
```

- 主路 RTSP 只允许 GStreamer `mppvideodec format=BGR` direct-BGR。
- 该路径由 gst-rockchip 内部通过 fd/DMA-BUF 使用 RGA，是当前唯一经过实机验证的允许方式。
- GStreamer direct-BGR 打开失败时，主路 RTSP 按读流失败处理。
- 主路 RTSP 不允许回退到 FFmpeg 硬解。
- 主路 RTSP 不允许回退到 GStreamer `videoconvert` safe 管线。

### 4.2 离线文件例外

- 离线测试视频可以保留不使用RGA的解码方式，以支持问题复现和自动回归。
- 离线文件链路不得恢复任何显式 RGA resize 或 `scale_rkrga`。
- 离线回放与现场 RTSP 必须在代码和测试中明确区分，不能共用模糊的 `auto` 回退语义。

### 4.3 永久禁止项

- 禁止恢复 `ffmpeg_rga`、`scale_rkrga`。
- 禁止恢复 `wrapbuffer_virtualaddr`、`imresize` 等虚拟地址RGA路径。
- 禁止在未完成独立实机错误路径验证前引入新的显式RGA调用。
- 禁止在 Web 操作员页面开放解码后端和RGA开关。

## 5. 产品与事件口径

- 甲方产品语义为“一车一次冲洗”。
- 一次物理车辆生命周期对应一个稳定业务 `event_id`。
- type1～type6可继续作为阶段更新，但同一车辆的所有阶段、纠错和重发必须使用相同 `event_id`。
- 甲方接口暂不增加 `revision` 或 `idempotencyKey` 公共字段；板端可维护内部 revision。
- 甲方平台必须将 `id` 作为更新同一记录的业务键。若同ID仍新增记录，上报层改造暂停并先完成甲方接口协调。
- tracker ID只是算法观测ID，不能继续承担最终业务ID职责。
- 行驶正向和反向均允许；`flow_vector`只负责方向分类，不作为事件准入条件。

- [ ] 原始识别值和原始事件证据永久保留，不允许被修订值覆盖。
- [ ] 默认保留90天数据。
- [ ] 磁盘使用率超过85%时，仅清理已结束且已成功上报的最旧事件。
- [ ] 待确认、上报失败和未结束事件禁止自动清理。

### M5：事件台账展示层

- [ ] 第一版只做事件台账和复核，不开发实时视频大屏。
- [ ] 支持日期、车牌、车型、事件状态、有效性和上传状态筛选。
- [ ] 支持分页，避免直接扫描全部历史文件。

## 7. 重点验收场景

- [ ] 静止边缘车辆持续30分钟不产生业务事件。
- [ ] 同一车辆检测消失少于8秒且tracker ID变化时，业务ID保持不变。
- [ ] 连续两辆外观相似且无有效车牌的车辆不会被错误合并。
- [ ] 车辆可从前门或后门进入，并得到正确的正向或反向分类。
- [ ] 同门进入又同门离开被标记为掉头或异常。
- [ ] 程序重启后，区域内车辆可以续接未结束事件。
- [ ] 一个物理车辆在甲方平台最终只形成一条可持续更新的冲洗记录。
- [ ] 人工纠错后使用原业务ID重发，本地保留完整原值和审计记录。
- [ ] 网络重试、进程重启和重复点击重发不会在板端生成重复outbox任务。
- [ ] 冲洗道与绕行道的事件数据库、查询、修订和清理互不串数据。
- [ ] 在25 FPS输入且处理约16～17 FPS的压测中，跟踪ID不会因丢旧帧和帧号跳跃产生可观测的系统性分裂。
- [ ] 无车辆画面连续运行5分钟时，绕行道不执行持续全图车牌推理，不产生车辆事件。
- [ ] 双车牌FLOAT16和INT8候选模型具有可重复的分阶段板端性能与精度对比报告。
- [ ] type1～type6阶段顺序符合状态机约束，不再出现type2先发送、type1后进入缓冲区。
